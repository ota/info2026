# 教材Webページと編集フローの改善案

2026年9月28日作成。これまでのやり取りと現行ソースを確認してまとめた提案です。以下の変更は未実装です。

追記：先生のWYSIWYGの好みを踏まえ、編集画面については末尾の「11. 表示を見ながら編集する案」を優先候補とします。Markdownは保存形式として維持し、普段の操作は画面上の編集に寄せる方針です。

おすすめは、**「Markdownで授業を作る」「Zedで自分の言葉に直す」「ブラウザで確認する」という流れを中心に、編集しても壊れにくい仕組みを整えること**です。第1回の形式をそのまま全回へ広げる前に、第2・3回も作って共通部分を見極めるとよいと思います。

## 1. これまでの試行錯誤から分かったこと

今回の修正には、一貫した方針があります。

| 大切にしていること | 教材づくりに落とし込むルール |
| --- | --- |
| 本科2年生が無理なく読める | 新しい用語は説明してから使う。「低レイヤ」のような用語のカギカッコも編集意図として扱う。 |
| シラバス・元資料との対応 | 講義名はシラバスに合わせる。元資料の説明・図・例を削るときは、その教育上の役割を確認する。 |
| 学習に集中できる画面 | キャッチコピー、飾りの英語、自明な小見出し、重複する操作説明を増やさない。 |
| 意味のまとまりが見える文章 | 一つの箇条書きに一つの要点を置く。理由や例は、その要点の下に置く。 |
| 手を動かして学ぶ | 見本と入力欄を近くに配置する。入力・実行・修正の往復を短くする。 |
| 先生が直接修正できる | 本文の変更にHTMLやJavaScriptの知識を要求しない。 |

こちらが元資料を短くしすぎたり、演出を加えたりしたことが、修正の往復を増やしました。この方針を短い「編集方針」として残し、次回以降の作成・仕上げの基準にするのが最も効果的だと思います。

「短い文章」を機械的な文字数制限にしないことも大切です。用語の説明まで削ると、学生が自分で補わなければならない情報が増えます。削除候補は、まず重複する案内や役割のない装飾文です。

## 2. 手作業とCodexを組み合わせるおすすめの流れ

### 1回分を作る流れ

1. **Codexが原資料から下書きを作る。** シラバスの到達目標、元スライドの説明・図・演習を対応づけてからMarkdownにする。追加した説明や省略した項目は、レビュー用の短いメモに残す。
2. **先生がZedで本文を直す。** 語彙、説明の順序、学生への指示、演習の難しさを調整する。プレビューは実際の教材をブラウザで開いて確認する。
3. **Codexが差分を中心に整える。** 箇条書きの構造、表記の揺れ、リンク、コードの動作、生成エラーを確認する。意味や教え方に関わる変更案は、元の文と修正案を並べて示す。
4. **先生が教材として確認する。** 特に新しい用語、元資料からの省略、演習の到達点を見る。
5. **指定した範囲まで公開する。** 依頼時に「ローカル確認まで」「公開まで」を決める。公開まで依頼した場合は、同じ承認を繰り返さず、検証から公開まで進める。

先生とCodexが同じMarkdownを同時に編集するより、手作業を保存したところで引き渡す運用をおすすめします。仕上げに入るときは、まず現在の差分を読み、先生が直した語彙や説明を基準にします。

依頼文は、例えば次の程度で十分です。

> 第2回のMarkdownを手直ししました。私が直した語彙と説明の順序を基準に、箇条書き・表記・動作を確認してください。意味を変える案は別に示し、今回はローカル確認までお願いします。

### Zedでの手間を減らす

Zedには作業コマンドを登録する仕組みがあります。「教材を開く」「公開前の確認」の2つを登録すれば、毎回ターミナルのコマンドを思い出す負担を減らせます。これは設定追加の提案です。[ZedのTasks公式説明](https://zed.dev/docs/tasks)

現在の専用記法は、この教材の生成処理が解釈しています。そのため、完成形の確認にはブラウザのプレビューを使うのが確実です。Zedは本文の編集場所として使います。

Markdownの自動整形は、専用ブロックや意図した箇条書きを壊さないか確認してから有効にします。また、見えない「行末の空白2個」に改行を依存させない方が編集しやすくなります。Zedは既定で保存時に行末空白を削除します。[ZedのMarkdown公式説明](https://zed.dev/docs/languages/markdown)

### 作業の保存と学生への公開

現在は `main` へのpushが、そのまま公開につながります。下書き作業が増えてきたら、作業ブランチで変更を保存し、授業用として確定した変更を `main` にまとめる運用が合っています。Git操作はCodexに任せ、先生は差分と画面を確認する形でよいと思います。

手動公開も選択肢ですが、毎回ボタンを押す手間が増えます。まずは「作業ブランチ→確認→mainに反映→自動公開」をおすすめします。GitHub PagesはGitHub Actionsによる公開に対応しています。[GitHub Pagesの公開元設定](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)

## 3. 教材を増やす前に、Markdown生成を整理する

現在のMarkdown化で本文は編集しやすくなりました。ただし、生成処理にはまだ第1回に合わせた仕組みが残っています。

| 現在確認できる構造 | 改善案 |
| --- | --- |
| `:::about-c` という第1回専用の記法がある | 「説明＋図」の共通部品にする。画像は通常のMarkdown記法で扱える範囲を増やす。 |
| `goals`、`warmup`、`challenge`、`summary` というIDが見た目も決めている | IDは保存やリンクのために固定し、見た目は別の指定で決める。見出しや並び順を直しても機能が変わらないようにする。 |
| タイトル・回数が複数のメタデータに重複する | 回数と講義名を1か所に書けば、ページタイトル・目次・フッターを組み立てる。 |
| 見出しと専用ブロックを正規表現で切り出している | Markdownパーサーのトークンを使い、コードの中身と見出しを区別して処理する。 |
| 先頭情報がYAML風の独自形式で、LF改行を前提に読む | Windowsの改行も受け入れ、使える形式を明文化する。標準形式を使うなら対応した読込処理にする。 |
| 生成したHTMLと見本用JavaScriptもGitで管理している | 将来的には生成物を専用ディレクトリにまとめ、レビューの差分をMarkdown・テンプレート・機能コードに集中させる。移行時に開発と公開の両方を確認する。 |

`markdown-it` はMarkdownをトークン列にして扱う機能を備えています。既に使っているライブラリの機能を利用する改善なので、これだけのために別の大きなシステムへ移行する必要はありません。[markdown-itの設計説明](https://markdown-it.github.io/markdown-it/documents/Architecture.html)

専用記法は、演習・ヒント・補足・図など、授業で何度も使うものに絞るのがよいと思います。色や配置を指定する記法を本文に増やすと、先生が文章と一緒にレイアウトも管理することになります。

生成エラーも編集作業の一部として扱います。「27行目の演習ブロックが閉じていません」のように場所と直し方を示し、失敗時は最後に正しく生成できたプレビューを残す形が使いやすいです。

Cの見本を通常のコードフェンスで書いた場合と、`:::exercise` 内に書いた場合で、コピーの可否が変わる点も統一したいところです。先生が表示方式を意識しなくても、授業上の「見本」が同じ規則で描かれる設計をおすすめします。

## 4. 見た目は共通ルールを少数にする

今の方向を維持し、次の部分を揃えると読みやすさを改善できます。

- **文字の大きさをまとめて調整する。** 現在の見本はCanvasで14pxを指定しており、本文のサイズ変更とは別です。本文・見本・入力欄のサイズを共通の設定から変えられるようにする。初期候補は本文18px前後、コード17〜18px程度とし、演習室の画面で確認する。
- **帯は主要な区切りに使う。** 小さな説明までカードや見出しにせず、段落・箇条書き・余白でまとまりを表す。
- **箇条書きは内容の関係で下げる。** 上位には要点、下位には理由や例を置く。深さを増やしすぎた箇所は文章の構成を見直す。
- **ブラウザの幅に応じて折り返す。** 見た目だけのために固定の改行を大量に入れず、文を分ける・箇条書きにする・文節の折り返しを調整する。
- **図は説明上の役割で残す。** ロゴ、概念図、出力例などを、単なる飾りとしてまとめて削らない。
- **通常時の状態表示を簡潔にする。** 同じ自動保存の説明が全入力欄に並ぶ状態は減らし、保存できなかったときは該当欄で明確に知らせる。

コピー防止に使うCanvasについても、拡大して読めることと、必要な学生に別形式の見本を提供できることは用意しておきたいです。演習室では通常表示に加え、ブラウザを125〜150%に拡大した状態も確認します。

## 5. Web教材としての発展案：写経の次を設計する

第1回の写経は、記号の入力や実行手順に慣れる活動として位置づけます。その後の理解を確認する活動を、小さく続ける構成がおすすめです。

1. 見本を入力して動かす。
2. 1か所変えると何が起こるか予想する。
3. 変更して実行し、予想と比べる。
4. 見本を離れて、小さな課題を解く。

例えば変数の型なら、「`number` を10から20へ変えると、どの行の出力が変わるか」で十分です。必要な演習だけ「変更した箇所と、結果の違い」を1行で書かせる案もあります。全問題に長い振り返りを付ける必要はありません。

第2・3回では、まずこの流れを少数の問題で試し、学生がどこで止まるかを見たいです。学習効果が確認できたという主張ではなく、授業で試す構成案です。

貼り付け禁止の範囲も、各回の目的に合わせて選べるようにすると発展性があります。初回は写経を重視し、後の回では自分のコードの再利用を認める、といった運用です。現在の禁止方針を変える場合は、授業方針として先に決めます。

実行結果については、正誤表示に加えて、コンパイル警告も扱いたいです。現行コードでは、実行成功時に警告を十分表示できるか見直す余地があります。原文を残しつつ、よくあるエラーだけ短い補足を出す方式なら、先生が説明内容を管理できます。

## 6. 自動保存は、共用PCでの運用から考える

最初に確認したいのは、演習室のPCで学生ごとにOSアカウントやブラウザの保存領域が分かれているかです。

現行の保存キーは講義回と演習を基準にしており、学生本人を区別していません。同じブラウザプロファイルを使い回す環境なら、前の利用者のコードが復元される可能性があります。`localStorage` は同じオリジンのデータをブラウザの再起動後も保持します。[MDNのlocalStorage説明](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

個別アカウントで十分に分離されていれば、追加操作を増やす必要はありません。共用の場合は、受講セッションの切り替えと復元対象の識別を設計します。常時表示する「入力を消す」ボタンを再び追加する必要はありません。

保存するデータは、次の組にすると扱いやすくなります。

- 講義ID・演習ID：見出しや並び順を変えても固定する。
- 現在のコードと最終更新日時：クラッシュ後の復元に使う。
- 最後に実行したコードと結果：現在の入力との対応を確認できるようにする。
- 教材の版：問題文を更新した場合の確認に使う。

見出しを変更しただけで入力が消えたり、問題の順番を変えたら別の回答が復元されたりしないことを、仕様として決めておきます。コードを編集した後に古い実行結果を復元する場合は、過去の結果だと分かる表示が必要です。

演習室では、実際の学生用アカウントで「入力→再読み込み→ブラウザ再起動→復元→保存→Moodle提出」まで1回通して確認したいです。README上はコンパイラの初回読込が約29MBあるため、クラス全員が初めて使うときの通信も確認対象です。

## 7. 提出物は、採点しやすさからも設計する

現在の「入力済みのページ全体を1ファイルで保存する」方式は、学生が自分の学習内容を残す用途にも使えます。これを維持しつつ、教員側では回答だけを素早く見られるようにする案をおすすめします。

**回答を構造化したデータを元に、教材ページと提出ファイルを作る**形にすると、画面の説明文を削っても保存処理が壊れにくくなります。今回のラベル削除による不具合を、設計から減らせます。

将来の提出用HTMLには、講義・演習ID、教材の版、入力済みコード、対応する実行結果などを機械で読める形でも埋め込みます。学生の操作は今と同じ「保存→Moodle提出」にできます。このデータは改ざん防止の証拠にはしません。

その先に、先生のPCで提出ファイルをまとめて読み込み、「課題1を全員分」「ある学生の全課題」と切り替えて確認できる採点用ビューアを作る案があります。毎回、長い教材本文をスクロールして探す作業を減らせます。取り込んだ学生ファイルのスクリプトは実行せず、回答データを表示する設計にします。

教材の版は、提出ファイルの短い表示と内部データに持たせれば十分です。ハッシュ等を使っても、それ自体が本人性を証明するわけではありません。

### 捏造対策への考え方

ローカルのログや端末情報を増やしても、自分で考えて入力したことの証明にはなりません。公開ページ内の秘密鍵や署名処理も、信頼できる発行者の代わりにはなりません。

評価には、提出したコードの一部を授業中に変更させる、1行の意味を説明させる、といった確認を組み合わせる案を優先したいです。入力速度や打鍵数を、理解度や不正の判定に直結させるのは避けます。

正式な提出受付はMoodleに任せる運用が自然です。Moodleの課題にはファイル提出、受付期限、提出確定などの設定があります。学校の実環境で、HTMLの許可・容量・教員によるダウンロードと閲覧まで確かめます。[Moodleの課題設定](https://docs.moodle.org/502/en/Assignment_settings)

別途サーバーを作る場合も、単にクライアントから送られたログに署名するだけでは、送信前の捏造を防げません。サーバーが観測した受付や実行と、自分で考えたことの確認は、それぞれ扱う必要があります。GitHub Pagesは静的ホスティングなので、こうした受付処理には別の実行環境が必要です。[GitHub Pagesの説明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

端末情報は、必要な場合の動作不良調査に使う程度に整理し、採点画面では回答を優先して見せる方がよいと思います。

## 8. 後期全体を見た、実行環境の方針

保存済みの講義計画では、第8回に標準入力・コマンドライン引数、第12回以降にLaTeXがあります。現在のC実行欄だけで全回を扱える前提にはできません。

| 授業内容 | 早めに確認すること |
| --- | --- |
| Cの基本、分岐、ループ、配列、関数 | ブラウザ実行を継続できるか。ループの回では、実行中だけ停止操作を出す案も検討する。 |
| 標準入力・コマンドライン引数 | 現在のWorkerはコードを受け取り、標準入力に空文字を渡している。入力用の欄、引数、出力との対応が必要になる。まずバッチ入力で授業目標を満たせるか検討する。 |
| 再帰・アルゴリズム | 実行できることに加え、呼出しの順序や値の変化を追う小さな図・表が役立つか試す。 |
| LaTeX | 教材本文・演習指示・提出の枠組みは共通化する。組版は学内環境や既存の環境も候補にし、日本語・数式・参照を含む小さな実例で確認してから選ぶ。 |

LaTeXのブラウザ実行環境まで一度に自作することは、現段階ではおすすめしません。CとLaTeXで実行部分を差し替えられる設計にし、授業上必要な機能を確認してから実装範囲を決めるのが現実的です。

将来の図や画像については、保存ファイルへの埋込みも共通処理にしたいです。現行の書き出し処理は見本CanvasとC言語ロゴを個別に扱っているので、図が増える回では、そのまま保存できるとは限りません。

## 9. 抜本的な改革案を選ぶなら

### 案A：授業本文と演習の情報を整理し、複数の表示を作る

同じ原稿から、学生が使う教材、投影しやすい表示、印刷用、提出用HTMLを作ります。先生の通常作業は1つのMarkdownの編集で済む形を目指します。投影用は文字や横幅を調整する程度から始め、別の資料を毎回作る負担を増やしません。

演習のID、見本、入力方法、確認事項が整理されると、教員向けの採点ビューアにもつなげられます。別形式の大量生成を先に作るより、実際に必要になった表示から追加するのがよいです。

**この案を最もおすすめします。** 今のMarkdown化を活かせ、文章の変更が保存機能に影響する問題にも対処できます。

### 案B：既成の静的サイト生成基盤へ移す

複数年度・複数教員で運用する規模になったら、AstroのようにMarkdownと共通レイアウトを扱う基盤も候補になります。AstroにはMarkdownからページを作る機能があります。[AstroのMarkdown公式説明](https://docs.astro.build/en/guides/markdown-content/)

一方で、写経入力・C実行・自動保存・提出HTMLは、この教材固有の機能として保守が必要です。基盤を替えるだけで解決する範囲は限定されます。まず第2・3回を作り、独自の生成処理の保守が負担になるかを判断材料にするのがよいと思います。

### 案C：Moodleとより深く統合する

ログイン済みの学生と回答を結び付ける、自動で正式提出する、教員が途中経過を確認する、といった要求が強くなれば候補になります。その場合は学校側の設定・利用できる連携方法・管理者の協力を確認する必要があります。

今は「公開教材を読む・動かす→HTMLを保存→Moodleに提出」を試し、手間が実際に大きい箇所を確認してから検討するのがおすすめです。

なお、解答・教員用メモを用意する場合は、現在の公開リポジトリの外、または非公開の保管場所で管理します。ページに表示しない設定だけでは、公開されたソースから読むことを防げません。

## 10. 着手順の提案

| 順番 | 取り組むこと | 完了の目安 |
| --- | --- | --- |
| 1 | 編集方針を短く固定し、Zedでの編集・ブラウザ確認・公開範囲を決める | 先生が本文を修正し、Codexが意図を保って仕上げられる。 |
| 2 | 演習室で保存とMoodle提出を一巡する | 実際の学生用環境で再読み込み・再起動・提出後の閲覧まで確認できる。 |
| 3 | 第2・3回を作りながら、専用記法と固定IDへの依存を整理する | 新しい本文や演習を追加するために、生成処理を毎回変更する必要がなくなる。 |
| 4 | 保存データを整理し、教材の版と回答の対応を持たせる | 見出し変更・並べ替え・文章削除の後も、入力の復元と提出が成立する。 |
| 5 | 採点の手間を見て、教員用ビューアを検討する | 提出物の読み比べや確認にかかる時間を減らせる。 |
| 6 | 第8回の入力・引数、LaTeX回の環境を小さく試す | 本文を作り込む前に、実行環境が授業目標を満たすか判断できる。 |

番号は実装規模の順序です。第8回・LaTeXの実現性確認は、大きな制約が見つかる可能性があるので、早い段階で短く試す価値があります。

確認の量は変更に合わせます。本文の修正は生成と表示を確認し、保存・実行機能を変更したときはブラウザで動作を確認します。見出し・ラベルの削除や演習の並べ替えでも保存できることは、今回の経験から、少数の自動チェックを残す価値があります。

当面は、第1回の仕組みを使って次の数回を作り、先生の編集しやすさと演習室での使い勝手を基準に改善を選ぶ方針をおすすめします。

## 11. 表示を見ながら編集する案

Web表示を常に見ながらMarkdownを編集することも、表示された文章を直接編集してMarkdownへ保存することも可能です。先生の好みを踏まえると、最終的には後者を中心にするのが合っていると思います。

| 方法 | 操作 | 現在の構成での実現性 |
| --- | --- | --- |
| Zedとブラウザを左右に並べる | ZedでMarkdownを保存すると、横の実際の教材ページが更新される | 現在の開発サーバーが対応済み。最も早く使える。 |
| ブラウザ内の左右分割画面 | 左にMarkdown、右に実際の教材表示。編集箇所と表示位置を対応づける | 追加実装が必要。入力中のプレビュー、スクロール連動、ファイル保存を組み込む。 |
| 教材ページ上で直接編集する | 本文をクリックして修正し、箇条書きの階層や表も画面で操作する | 教員用の編集画面を追加する。専用の演習ブロックを扱えるようにする必要がある。 |

ZedにはMarkdownの横並びプレビューもあります。ただし、教材独自の `:::exercise` やCanvas描画を含む完成形の確認には、この教材の生成処理を通したブラウザ表示を使います。[Zedのプレビュー操作](https://zed.dev/docs/all-actions)

### おすすめする教員用編集画面

通常は教材と同じ文字・色・幅で表示し、編集したい段落をクリックすると、その場で書き換えられるようにします。箇条書きの追加や階層変更、太字、リンクなどは小さなツールバーで操作する案です。

見本コードは先生用のコード編集欄で変更します。ここでは貼り付けを使えます。演習の見本、学生の解答欄、実行結果は別の要素として扱い、教材編集の操作で学生用の入力欄を書き換えてしまわないようにします。

保存先は引き続き `content/lesson01.md` とし、Codexも同じ原稿を扱います。初期の試作範囲は、本文・箇条書き・見本コードの編集に絞るのがよいです。表や画像、ブロックの並べ替えは、使い勝手を確認してから広げられます。

ブラウザ上の変更をMarkdownへ戻す処理は追加開発が必要です。例えばTiptapにはMarkdownの読込・書出しや独自ブロックを拡張する仕組みがありますが、確認時点のMarkdown機能はBeta表記です。採用は試作で判断し、この教材の専用記法は個別に対応します。[TiptapのMarkdown説明](https://tiptap.dev/docs/editor/markdown/getting-started/basic-usage)

保存時には、階層付き箇条書き、カギカッコ、コードの空白、演習IDが保たれるかを確認します。ページ全体の表示HTMLを一括でMarkdownへ逆変換する方式は、この教材では余分なUIやCanvasを含んでしまうため、本文・演習の情報を単位に保存する設計が必要です。

先生のPC上で動く編集用サーバーにファイル保存を任せれば、編集のための外部サービスを新設せずに構成できます。編集機能は開発環境でだけ提供し、学生向けの公開物には含めません。保存とGitHub Pagesへの公開は別の操作にします。

Zedと教員用編集画面の両方で同じファイルを開く場合は、保存前に外部変更を確認し、片方の変更を黙って上書きしない仕組みも必要です。

当面の使い方はZedと実際のWeb表示の併用、次の試作候補は「文章をクリックして修正できる教員用画面」をおすすめします。これは編集操作の変更案であり、今回の追記時点では機能を追加していません。
